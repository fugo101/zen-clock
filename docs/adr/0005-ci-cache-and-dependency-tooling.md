# CI cache and dependency tooling

**Rationale for non-obvious sdkconfig/Kconfig choices lives in prose docs (ADRs, `CLAUDE.md`), never
in `sdkconfig` comments.** `pio run`'s confgen step regenerates `sdkconfig.lilygo-t-display-s3` and
wipes hand-edited comments on every run — only the values survive. A comment explaining a non-default
Kconfig choice would silently vanish the next time anyone runs a build.

**There is no CI drift check for `sdkconfig.lilygo-t-display-s3`, deliberately.** `dependencies.lock`
can be drift-checked cleanly because it carries a stable `manifest_hash` regenerated by the build, so
`git diff --exit-code` is a clean pass/fail signal. A generated-and-rewritten sdkconfig has no
equivalent stable diff target, so the same check would risk failing on churn that isn't a real
regression. The credential-leak risk that would otherwise motivate this check is covered separately
by `scripts/check_secrets.py`.

**GitHub Actions are pinned to moving major version tags (`@v7`), not commit SHAs — a maintainer
decision, not an oversight of the usual supply-chain-hardening advice.** `.github/dependabot.yml`
proposes major version bumps as PRs instead, keeping the tradeoff visible and reviewable rather than
frozen. Don't SHA-pin this repo without discussing it first.

**Release Please authenticates via a short-lived GitHub App token, not `GITHUB_TOKEN` or a PAT.**
`GITHUB_TOKEN`-authored PRs don't trigger downstream workflows, so CI would never run on the Release
PR itself if Release Please used it directly — a PAT was used originally to work around that, but a
PAT is a human's credential: it expires silently, and when it does, Release Please just stops opening
Release PRs with no visible error. `actions/create-github-app-token` mints a short-lived, repo-scoped
token per run instead, removing that silent-failure mode.

**The CI job's `name:` field is the required-status-check contract with the `main` branch ruleset,
and must never be renamed without also updating the ruleset.** Renaming the job alone means the
required check never reports again, which blocks every PR from merging indefinitely — including the
PR that would fix the rename. A consequence worth remembering: with exactly one self-hosted runner
behind that one named check, a runner outage now blocks all merges rather than just delaying CI
feedback.

**Docs-only PRs skip the build/test/analyze steps via an in-job allow-list, not a workflow-level
`paths-ignore`.** A `paths-ignore` at the workflow level would skip the whole job, and since the job's
name is the required-status-check contract above, the check would then never report at all — blocking
every docs PR forever instead of fast-passing it. The in-job "detect build-relevant changes" step
instead diffs against the PR base with an inverted, fail-safe allow-list: only doc-shaped paths
(`docs/`, `README.md`, `CLAUDE.md`, `CHANGELOG.md`, `THIRD_PARTY.md`, `LICENSE`, editor-config dirs)
are considered inert, and anything not on that list — including a path never seen before — forces a
full build. `version.txt`, `dependencies.lock`, and `sdkconfig.*` are deliberately excluded from the
allow-list so a Release Please PR still gets a full build.

**The self-hosted runner's PlatformIO build cache is redirected outside the workspace `actions/checkout`
cleans, and namespaced by a hash of the files that can invalidate it.** `actions/checkout` defaults to
`clean: true` (`git clean -ffdx`), and `.pio/`/`managed_components/` are both gitignored, so without
this every CI run rebuilt all ~2200 objects from zero even though the runner's `$HOME` persists
between runs — measured at ~9 minutes, 94% of total CI time. Pointing
`PLATFORMIO_BUILD_CACHE_DIR` at a directory under the runner's `$HOME` lets SCons's own content-addressed
`CacheDir` (PlatformIO/espidf builds through SCons, not ninja — ninja only runs for `menuconfig`)
survive the checkout's clean step; measured cold build 89s, cache-retrieved rebuild 5.9s, bit-identical
firmware. The cache directory is namespaced by `hashFiles(sdkconfig.lilygo-t-display-s3,
platformio.ini, dependencies.lock)` because ESP-IDF 6.x passes compiler flags to SCons via response
files, and SCons's build signature is computed from the command line — a flag change (e.g. an
optimization-level edit) that leaves the response-file *path* unchanged would otherwise be invisible
to the cache and silently serve stale objects. A plain flat cache directory was considered and
rejected for exactly that reason. `actions/cache` (uploading the cache to GitHub's servers) was also
considered and rejected as the primary mechanism: with a single persistent self-hosted runner, reading
from local disk costs nothing, while shipping several hundred MB over the network on every run only
buys resilience against a runner rebuild — a scenario that costs one cold build either way. This cache
has no eviction by itself (each unique sdkconfig/platformio.ini/dependencies.lock combination is a new
~285MB namespace); the CI prune step relies on `os.utime()` being called on every cache hit
(`CacheRetrieveFunc`, unaffected by `relatime`) to make `find -atime +14 -delete` a reliable
"still in use" signal rather than a guess.

**`microlink` and `wireguard_lwip` are ESP Component Registry dependencies, not vendored git
submodules.** The registry migration removed the submodule-specific failure modes this project used
to carry (remote-rewriting on `git submodule sync`, submodule-pointer bump races on merge) in
exchange for depending on two components this project doesn't control the release cadence of;
`THIRD_PARTY.md` and each dependency's own `UPSTREAM_PRS.md`-style history now carry provenance
instead of hand-maintained prose here. `idf: ">=6.0.0"` was tightened to `<7.0.0` for the same reason
in the other direction — this project carries ESP-IDF 6.x-specific patches that an unannounced 7.x
jump would break, so the upper bound is deliberate, not a default.
